# Sanad Review — أداة الرد التلقائي (مسودات) على تقييمات Google

> **v2 — إعادة بناء كاملة من الصفر.** نفس الفكرة الأساسية اللي أثبتت نفسها بالنسخة الأولى، لكن ببنية
> كود احترافية (طبقات منفصلة: config / db / middleware / services / routes / views)، حماية أقوى
> (CSRF, rate limiting, HTTP security headers)، اختبارات آلية حقيقية، وميزات جديدة (استرجاع كلمة
> المرور، صفحة إعدادات الحساب، رسم بياني لتطور التقييم، ردود جاهزة محفوظة).

منصة SaaS متعددة العملاء (multi-tenant): كل نشاط تجاري يسجل حساب، يربط حساب Google Business Profile
الخاص فيه، ويحصل على مسودة رد جاهزة لكل تقييم جديد. **الاشتراك (35$/شهر) لكل نشاط تجاري لحاله** —
حساب المستخدم الواحد يقدر يربط أكثر من فرع/بزنس، لكن كل فرع له اشتراكه المستقل، يُفعّل بالدفع بعد ربطه.
**افتراضياً، كل رد يبقى مسودة** لحد ما صاحب العمل يراجعه ويضغط زر "نشر" بنفسه. يقدر صاحب العمل يفعّل
"النشر التلقائي للإيجابي" اختيارياً — راجع قسم "النشر التلقائي الذكي" تحت لتفاصيل الحماية.

## ⚠️ اقرأ هذا قبل أي شي: هل تقدر تبيعها "من اليوم الأول" فعلاً؟

بنيت لك النظام التقني كامل (تسجيل، دفع، لوحة تحكم لكل عميل). لكن فيه بوابتين خارج سيطرتي لازم تجتازهم
قبل ما تقدر تاخذ أول ريال حقيقي من عميل حقيقي:

1. **موافقة Google على وصول تطبيقك لـ API التقييمات** — طلب رسمي تقدمه أنت، يمديها من أسبوعين لأسابيع.
2. **Google OAuth verification** — قبل ما يقدر أي عميل *غيرك* يربط حسابه بالأداة، Google يتطلب توثيق
   التطبيق (دومين حقيقي + سياسة خصوصية + شروط استخدام + فيديو توضيحي). بدون هذا، Google يوقف أي مستخدم
   خارج قائمة "Test users" المحدودة (100 مستخدم كحد أقصى، ولازم تضيف كل بريد يدوياً).

بما إن كل بيانات اعتماد Google/Stripe القديمة انحذفت، هذي البوابتين لازم تُعاد من الصفر بحسابك أنت —
هذا الجزء ما أقدر أسويه بدالك، لأنه يحتاج وصول لحساباتك الشخصية على Google Cloud وStripe. القسم
"2. المتطلبات قبل التشغيل" تحت فيه كل خطوة بالتفصيل.

**توصيتي:** خلّي مفاتيح Stripe في وضع Test أول، اجمع تسجيلات "قائمة انتظار" أو عملاء تجريبيين مجاناً
لحد ما تتأكد إن ربط Google يشتغل بشكل مستقر مع أكثر من نشاط تجاري حقيقي، وبعدها فعّل مفاتيح Stripe
الحقيقية (Live mode) وابدأ الفوترة الفعلية. غير كذا راح تضطر ترجع فلوس لعملاء دفعوا والمنتج ما يشتغل
لهم لأن حسابهم على Google لسه ما انربط.

## 1. الفكرة العامة (رحلة العميل)

1. يدخل صفحة التسويق (`/`) ويضغط "ابدأ الآن".
2. يسجل حساب (اسم النشاط، إيميل، كلمة مرور) — مجاني، بدون أي طلب دفع في هذي الخطوة.
3. يربط حساب Google Business Profile (OAuth) ويختار النشاط التجاري (الفرع).
4. يتوجه لصفحة "الاشتراك" ليدفع 35$/شهر لتفعيل *هذا الفرع تحديداً* عبر Stripe.
5. يقدر يربط فروع/أنشطة تجارية إضافية بنفس الحساب في أي وقت (زر "+ Connect another business")،
   وكل فرع جديد يحتاج اشتراكه الخاص لتفعيله — الأداة ما تشتغل على أي فرع غير مفعّل.
6. يضغط "جلب التقييمات الجديدة" فتجيب الأداة أي تقييم جديد للفروع المفعّلة فقط، وتسوي له مسودة رد.
7. يراجع المسودة، يعدّلها لو يبي (أو يبدأ من رد جاهز محفوظ)، ويضغط "نشر على Google" بنفسه — وهذي
   اللحظة الوحيدة اللي الأداة تتواصل فيها مع Google لنشر رد (إلا لو فعّل النشر التلقائي، راجع القسم
   التالي).
8. يقدر يدير كل اشتراكاته أو يلغي أي واحد منها في أي وقت من صفحة "الاشتراك" (بوابة Stripe الرسمية
   الموحّدة — بطاقة دفع واحدة تدير كل الفروع).

## 1.1 النشر التلقائي الذكي (اختياري)

من لوحة التحكم، يقدر صاحب النشاط يفعّل **"النشر التلقائي للإيجابي"** لكل نشاط تجاري على حدة. لما يكون
مفعّل، أي تقييم جديد يحقق **الشرطين معاً** ينشر رده فوراً بدون أي مراجعة بشرية:

- التقييم 4 أو 5 نجوم
- التعليق (لو موجود) ما فيه أي كلمة تدل على شكوى أو استياء — قائمة كلمات محفوظة بـ
  `src/services/riskClassifier.js` تغطي **9 لغات** (عربي، إنجليزي، فرنسي، إسباني، ألماني، برتغالي،
  تركي، روسي، هندي)، مبنية بحيث ما تعطي إنذار كاذب على كلمات زي "ممتاز"/"excellent" اللي تحتوي جذور
  متشابهة لكلمات خطر.

أي تقييم ما يحقق الشرطين (3 نجوم فأقل، أو فيه إشارة سلبية بالتعليق حتى لو التقييم 5 نجوم) يبقى **مسودة
تنتظر مراجعة صاحب النشاط** زي المعتاد. الإعداد **معطّل افتراضياً** لكل حساب جديد — العميل يفعّله بنفسه
لما يثق بجودة الردود.

هذا يوازن بين "العميل ينسى الموضوع" (الأغلبية الإيجابية تُنشر تلقائياً) و"الحماية من رد خاطئ ينشر بالعلن"
(أي حالة فيها شك تتحول تلقائياً لمراجعة بشرية).

**كلمات خطر مخصصة**: من نفس اللوحة، كل نشاط تجاري يقدر يضيف كلمات خطر خاصة فيه (مثلاً مطعم يضيف
"بارد"/"متأخر") تُضاف لقائمة الكلمات الافتراضية وتوقف النشر التلقائي احترازياً.

## 1.2 ميزات لوحة التحكم

- **إحصائيات سريعة**: إجمالي التقييمات، متوسط النجوم، عدد التقييمات المنتظرة للرد، وعدد المنشورة —
  تظهر تلقائياً فوق اللوحة.
- **📈 رسم بياني لتطور التقييم**: رسم خطي بسيط (SVG، بدون أي مكتبة رسم خارجية) يوضح متوسط تقييم كل
  نشاط تجاري أسبوعياً على مدى آخر 8 أسابيع — يبين هل الأداء يتحسن أو يتراجع بنظرة واحدة.
- **📝 ردود جاهزة محفوظة**: كل نشاط تجاري يقدر يحفظ قوالب رد جاهزة (مثلاً "شكر عام"، "اعتذار عن تأخير")
  ويستخدمها كنقطة بداية سريعة عند كتابة رد يدوي، بدل ما يكتب من الصفر كل مرة.
  اسم القالب ≤80 حرف، النص ≤2000 حرف.
- **فلترة التقييمات**: حسب الحالة (تحتاج رد / منشورة) أو عدد النجوم.
- **تصدير CSV**: زر "تصدير CSV" يحمّل كل التقييمات وردودها كملف Excel-friendly (بترميز UTF-8 BOM
  عشان العربي يظهر صح).
- **نبرة الرد**: كل نشاط تجاري يختار نبرة الردود المولّدة (ودّية / رسمية / مختصرة) من إعداداته.
- **إشعار بريدي اختياري**: لما توصل تقييمات جديدة تحتاج مراجعة، الأداة ترسل إيميل تنبيه لصاحب الحساب —
  يشتغل بس لو ضبطت `RESEND_API_KEY` بـ `.env` (حساب مجاني على resend.com). بدون هذا المتغير، الأداة
  تشتغل عادي بدون أي إشعارات أو أخطاء.
- **📊 تحليل ذكي للأسباب المتكررة**: زر "حلّل تقييماتي الآن" لكل نشاط تجاري يقرأ التقييمات السلبية
  والمتوسطة (آخر 90 يوم) ويطلع أهم 3-5 أسباب شكوى متكررة فعلياً — مثلاً "3 عملاء ذكروا بطء الخدمة" —
  بدل ما صاحب العمل يقرأ كل تقييم بنفسه ليكتشف النمط. يستخدم Claude لو `ANTHROPIC_API_KEY` مضبوط
  لتحليل أعمق بالعربي، وإلا يرجع لعدّ تكرار الكلمات (نفس قائمة كلمات الخطر + كلمات النشاط المخصصة)
  كبديل بدون أي تكلفة. يحتاج 3 تقييمات سلبية/متوسطة فيها تعليق على الأقل عشان يعطي نتيجة مفيدة.
- **📮 التقرير الأسبوعي الذكي**: كل يوم اثنين 8 صباحاً (UTC)، كل عميل عنده اشتراك فعّال يستلم بريد
  مختصر بأسلوب طبيعي (مو جدول أرقام): عدد التقييمات هالأسبوع ومتوسطها مقارنة بالأسبوع اللي قبله، أبرز
  نمط شكوى متكرر (من التحليل الذكي)، وأفضل/أصعب تقييم وصله. يتولد تلقائياً عبر مهمة مجدولة
  (`src/services/scheduler.js` بمكتبة `node-cron`)، ويُرسل بريدياً بس لو `RESEND_API_KEY` مضبوط ووصل
  تقييم واحد على الأقل هالأسبوع — غير كذا يتولد ويتخزن بس (يظهر بزر "أرسل تجربة الآن" باللوحة، مفيد
  للتجربة الفورية بدون انتظار يوم الاثنين).
- **📣 كود QR ورابط لطلب تقييمات جديدة**: كل نشاط تجاري مفعّل (مدفوع) له رابط ثابت (`/r/<id>`) وكود QR
  يولّدهم النظام تلقائياً (`qrcode` npm package، بدون أي خدمة خارجية). أي حد يمسح الكود أو يفتح الرابط
  يروح مباشرة لصفحة كتابة تقييم جديد على Google لنفس النشاط (`metadata.newReviewUri` من Google Business
  Information API). صاحب النشاط يقدر يطبعه أو يشاركه بأي طريقة يبيها — الأداة ما ترسل أي رسائل نيابة
  عنه. يحتاج موافقة Google على API التقييمات عشان يظهر الرابط (نفس البوابة الموضحة بالأعلى).
- **⚙️ إعدادات الحساب**: صفحة `/settings` تسمح بتعديل اسم النشاط التجاري وتغيير كلمة المرور (يتطلب
  إدخال كلمة المرور الحالية أولاً).
- **🔑 نسيت كلمة المرور؟**: تدفق كامل استرجاع كلمة مرور عبر `/forgot-password` → بريد فيه رابط صالح
  لمدة ساعة → `/reset-password`. الرسالة المعروضة عامة دائماً ("لو الحساب موجود، بنرسل لك رابط") عشان
  ما نكشف هل إيميل معين مسجل عندنا أو لا. يحتاج `RESEND_API_KEY` عشان يرسل البريد فعلياً.

## 1.3 الأمان والبنية التقنية (جديد بالكامل بالنسخة v2)

- **بنية طبقات واضحة**: `src/config` (إعدادات البيئة والـ logging) → `src/db` (المخطط) →
  `src/middleware` (auth, أمان, csrf) → `src/services` (المنطق التجاري) → `src/routes` → `src/views`،
  بدل ملفات مسطحة بمجلد واحد.
- **حماية CSRF** على كل طلب POST بالتطبيق (توكن مخزن بالجلسة، حقل مخفي بكل نموذج).
- **HTTP security headers** عبر `helmet`، و**Rate limiting** (20 طلب/15 دقيقة) على مسارات التسجيل
  والدخول واسترجاع كلمة المرور لمنع محاولات التخمين المتكررة.
- **تسجيل أحداث منظم (structured logging)** عبر `pino` بدل `console.log` المبعثر.
- **اختبارات آلية حقيقية** (`npm test`، بمشغّل الاختبارات المدمج بـ Node، بدون أي اعتمادية إضافية):
  - `tests/riskClassifier.test.js` — يتحقق من مصنّف الخطر بـ 9 لغات، وإنه ما يعطي إنذار كاذب.
  - `tests/tenantIsolation.test.js` — اختبار تكاملي يشغّل التطبيق الحقيقي على منفذ مؤقت مع قاعدة
    بيانات معزولة، ويتأكد إن التسجيل يشتغل، إن CSRF يرفض الطلبات بدون توكن، وإن عميل ما يقدر يوصل
    لبيانات عميل ثاني.
- **فصل `app.js` عن `server.js`**: `src/app.js` يبني تطبيق Express الكامل بدون تشغيله، و`src/server.js`
  ملف تشغيل بسيط (`.listen()` + بدء المهمة المجدولة) — هذا يسمح للاختبارات الآلية تستورد التطبيق مباشرة
  بدون تعارض مع أي عملية تشغيل حقيقية.

## 2. المتطلبات قبل التشغيل

### أ) Google Cloud

1. https://console.cloud.google.com > مشروع جديد.
2. فعّل: **My Business Account Management API**، **My Business Business Information API**،
   **Google My Business API** (v4، لإدارة التقييمات).
3. ⚠️ قدّم طلب وصول لإدارة التقييمات عبر:
   https://developers.google.com/my-business/content/basic-setup#request-access
4. من "OAuth consent screen": نوع External، أضف Scope
   `https://www.googleapis.com/auth/business.manage`، وأضف بريدك (وبريد أي عميل تجريبي) كـ Test user
   لحد ما توثّق التطبيق.
5. من "Credentials": أنشئ OAuth client ID (Web application)، وأضف Redirect URI:
   - محلياً: `http://localhost:3000/auth/google/callback`
   - بعد النشر: `https://<دومينك>/auth/google/callback`

### ب) Stripe (الاشتراك الشهري)

1. أنشئ حساب على https://dashboard.stripe.com (يدعم شركات الإمارات).
2. من Developers > API keys: انسخ **Secret key** (استخدم `sk_test_...` وقت التجربة).
3. من Product catalog: أنشئ Product باسم "Sanad Review"، وProduct Price:
   - Recurring، شهري (Monthly)، 35.00 **USD**.
   - انسخ معرف الـ Price (يبدأ بـ `price_...`).
4. من Developers > Webhooks: أضف Endpoint جديد يشاور على `https://<دومينك>/billing/webhook`
   (محلياً استخدم Stripe CLI: `stripe listen --forward-to localhost:3000/billing/webhook`)،
   واختر الأحداث: `checkout.session.completed`, `customer.subscription.updated`,
   `customer.subscription.deleted`. انسخ **Signing secret**.
5. من Settings > Billing > Customer portal: فعّل الـ Customer Portal (يستخدمه العميل لإلغاء اشتراكه).

### ج) تجهيز الأداة محلياً

يحتاج جهازك Node.js نسخة 18 أو أحدث.

```bash
npm install
cp .env.example .env
```

افتح `.env` واملأ:

| المتغير | وش هو |
|---|---|
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | من خطوة Google Cloud |
| `GOOGLE_REDIRECT_URI` | `http://localhost:3000/auth/google/callback` محلياً |
| `SESSION_SECRET` | نص عشوائي طويل |
| `APP_BASE_URL` | `http://localhost:3000` محلياً، ورابط تطبيقك الحقيقي بعد النشر |
| `STRIPE_SECRET_KEY` | من Stripe Dashboard |
| `STRIPE_PRICE_ID` | معرف الـ Price اللي أنشأته (`price_...`) |
| `STRIPE_WEBHOOK_SECRET` | من إعداد الـ Webhook |
| `ANTHROPIC_API_KEY` | اختياري — ردود أذكى وتحليل أعمق عبر Claude بدل القوالب الجاهزة |
| `RESEND_API_KEY` | اختياري — بدونه: بدون إشعارات بريدية، بدون تقرير أسبوعي، وبدون بريد استرجاع كلمة المرور (لكن باقي الأداة تشتغل عادي) |

شغّل الأداة:

```bash
npm start
```

افتح `http://localhost:3000` — بتشوف صفحة التسويق، وتقدر تسجل حساب وتجرب الرحلة كاملة.

**تشغيل الاختبارات الآلية** (اختياري، لكن موصى فيه بعد أي تعديل بالكود):

```bash
npm test
```

## 3. النشر على Railway

1. https://railway.app > New Project > Deploy from GitHub repo (بعد ما ترفع الكود لمستودع خاص فيك).
2. Railway يشغّل `npm start` تلقائياً.
3. من Variables أضف نفس متغيرات `.env`، لكن:
   - `GOOGLE_REDIRECT_URI=https://<دومينك>/auth/google/callback`
   - `APP_BASE_URL=https://<دومينك>`
   - `NODE_ENV=production`
4. **مهم**: أضف نفس رابط الـ redirect الجديد في Google Cloud Console، وأضف Webhook جديد في Stripe
   يشاور على `https://<دومينك>/billing/webhook`.
5. من إعدادات الخدمة أضف **Volume** واربطه بمجلد `/app/data` عشان بيانات العملاء والتقييمات ما تضيع
   عند أي إعادة نشر (redeploy). هذا مهم جداً الحين لأنه صار فيه بيانات حسابات وفواتير عملاء حقيقيين.

## 4. حدود النسخة الحالية

- **لا نشر تلقائي على الإطلاق** — مبدأ ثابت، إلا بالنطاق الضيق والمُفعَّل يدوياً الموضح بقسم 1.1.
- الاشتراك حالياً خطة واحدة فقط (35$/شهر لكل نشاط تجاري، بدون تجربة مجانية)، بدون خصومات أو خطط سنوية.
- ما فيه إشعارات فورية (بريد/واتساب) عند وصول تقييم جديد بشكل لحظي — العميل يدخل ويضغط "جلب التقييمات
  الجديدة" يدوياً؛ الإشعار البريدي والتقرير الأسبوعي يغطون جزء من هذا لكن ما فيه دفع فوري (push).
- الجلسات (`express-session`) مخزنة بالذاكرة (in-memory) لا بقاعدة بيانات — يعني أي إعادة تشغيل للخادم
  (deploy جديد أو Crash) تسجّل خروج كل المستخدمين المتصلين، لكنهم يقدرون يسجلون دخول فوراً بدون فقد
  أي بيانات. هذا قرار مقصود لتفادي اعتمادية session-store كانت تسبب تجمّد بعملية الاختبارات.
- التسويق الفعلي (التواصل مع متاجر وشركات حقيقية) مسؤوليتك أنت — الأداة جاهزة لاستقبالهم تقنياً، لكن
